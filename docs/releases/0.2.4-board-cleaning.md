# 0.2.4: clean today's holds

Status: implemented on `feat/0.2.4-board-cleaning`, integrated into the 0.2.4
release line `feat/0.2.4-training-nutrition` on 2026-10-10; physical board
validation pending. This is Android feature work, not a published
0.2.4 release or a claim of iOS parity.

## Entry and behavior

Open **Logbook → ⋮ → Clean holds** (**Logbuch → ⋮ → Griffe putzen**).
The option remains available with an empty logbook. It offers board connection
when disconnected, identifies the connected controller, shows today's distinct
hold count and lights the combined holds in one color. Statistics and filters
keep their existing behavior; changing a logbook filter does not change this
explicitly daily, physical-board collection. Selection and deletion are in the
same overflow menu so the header still fits on narrow screens.

Closing the sheet leaves cleaning active. A persistent status button on board
screens reopens the controls. **Stop · keep collection** restores the last
known display; **Cleaned · reset collection** also clears this board's collection.
If the previous display is unknown after a reconnect/restart or a raw relay
write, finishing clears the LEDs. A failed restore retains the collection and
offers retry. Older API-2 controllers use sections when the collection exceeds
their power budget (250 holds on Kilter, 500 on single-LED boards). **These holds
are clean · next section** removes only the confirmed section and lights the next;
the final confirmation restores the previous display. Unfinished sections remain
collected. Disconnect ends the active mode without clearing collected holds.

## What is collected

- Only successful CruxCoach problem projections from this phone, including
  playlist/shared-session host sends and problems with no logged ascent.
- Physical positions after LED mapping/mirroring, deduplicated across roles,
  repeats and angles. Editor previews, color tests, animations and cleaning
  itself do not add holds. This is not touch detection: an illuminated problem
  may include holds the climber did not actually use.
- Each physical controller/family/protocol has its own installation-local
  collection. Restarting the app or changing accounts does not lose a group's
  collection on the same phone. There is no cross-phone aggregation or sync.
- The local calendar date defines “today”. Midnight starts a fresh collection;
  an already active cleaning round can finish with its original holds.
- Collection starts with this feature's installation. No reconstruction from
  old ascent/history rows: they do not reliably identify controller, mirrored
  state or the exact projected LED positions.

Only hashed controller keys, local dates and LED positions are persisted in
`board_cleaning` preferences. Old dates are pruned on the next recorded send.
No new personal logbook rows or projection-history rows are created by cleaning.

## Protocol and session boundaries

Aurora-family boards use single-channel blue with the connected encoder, preserving
API-2 power scaling and multi-packet framing. API-2 sections cap the number of
holds so every position stays nonzero at minimum brightness within the 18 W
budget; a large cyan union would otherwise quantize entirely to black. MoonBoard
uses its ASCII UART encoder with existing write pacing; cleaning marks each
physical hold below the hold, independent of above/both preview settings.

Quantum is unavailable: its existing adapter deliberately rejects unverified
multi-frame activation and requires scoped user/route ownership. This feature
must not bypass those guards to light an arbitrary day's union.

All local projection/clear/raw producers share the BLE write mutex and reject
writes during cleaning. The idle-disconnect timer is suppressed. Link changes
invalidate pending completions so an old write cannot clear another board's
collection. Other phones connected directly to a multi-client controller can
still overwrite its display; CruxCoach cannot lock those devices.

Relay guests are not included. Starting requires the phone's relay sharing to
be off and a direct physical-board connection; a relay phone address does not
identify a stable physical board. Group sessions controlled by this phone do
contribute through their ordinary projection path. Queue navigation is not
discarded or logged by cleaning; explicit normal sending resumes after exit.

## Validation

Focused tests cover daily union, persistence, controller separation, restart,
midnight, empty/unsupported state, stale connection completions, failed sends,
restoration and reset, MoonBoard mapping, >84-hold Aurora framing, and the UI's
separate keep/reset actions and busy/empty controls. Full checks run in CI.

Physical-device acceptance before release:

1. Send two overlapping problems, including a mirrored problem and an unlogged
   attempt. Verify the count and combined LEDs against the actual wall.
2. Open from the logbook, start, close the sheet and navigate. Ensure automatic
   sends and configured idle disconnect do not overwrite/end the cleaning mode.
3. Stop and verify the exact previous colors/positions; start again and mark
   cleaned, then send another problem to verify a fresh collection.
4. Reconnect/restart on the same board, switch to a second controller and return.
   Verify persistence/isolation and the clear fallback when no previous display
   is known. Interrupt a write to check error/retry and collection retention.
5. Repeat on Aurora API-2/API-3 and MoonBoard standard/Mini; include more than
   one packet of accumulated holds. Verify readability at 320 dp/200% font size.

Local checks: the first 20 focused tests passed before the additional API-2
section handling. The extended focused suite and full CI validate the final revision.
Feature CI: https://github.com/CruxCoach/CruxCoach/actions/workflows/feature-build.yml

No physical BLE validation has been performed for this change yet.
